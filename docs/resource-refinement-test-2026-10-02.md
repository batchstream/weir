# Weir 下一轮完善与复测（2026-10-02，v4）

本轮完善了控制器统计、RPC 取消隔离和写入结果判定，并用冻结的 v3/v4 构建做真实数据库对照。MongoDB 四轮背压测试均恢复至 2500 次成功/秒，v3 也同样恢复；因此此前的恢复残差没有在这次受控环境中复现。ES 参数调优后，极低配额阶段观察到 602/1270 次成功/秒，仍无法承载输入的 2500 次/秒。写入已被数据库确认与整个 RPC 成功分别统计，极端限额下的 UNKNOWN 和发送前丢弃均保留。

这里的 v3 是[上一轮重构后的构建](resource-goals-test-2026-10-02.md)，不是初始仓库版本。本轮重点是恢复和回归验证，没有重新运行直连/Weir 的完整 48 格性能矩阵，也没有实际部署 HPA。上一轮结果和原始证据保持不变。

## 实际改动

|改动|原因与现在的行为|验证|
|---|---|---|
|自适应控制器|用四个可比健康样本的均值建立基线，后续普通成功样本用 1/8 EWMA 双向更新；避免偶然极快样本永久压低基线。有排队的慢请求不能抬高基线，持续压力仍会减窗。旧窗口的成功完成只参与可比统计，不能改变新窗口或续期恢复 hold。取消请求不能稀释、擦除独立的压力证据。|覆盖极快初始样本、持续慢工作 4→1、正常工作恢复、旧窗口及取消隔离的测试和 race。|
|RPC 取消隔离|普通取消只缩短当前 HTTP/2 stream 的读写 deadline，避免关闭共享连接影响其他 RPC；真正的 stalled-peer watchdog 仍保留。|原行为下的复现失败，修复后的取消/真实 stall 测试及 10 次 race 均通过。|
|Search 未发送写判定|标准 HTTP Transport 明确尚未取得连接，或 Do 前已经取消时，返回 NOT_APPLIED。拿到连接后发生错误继续 UNKNOWN，不自动重试。|真实连接池等待取消、拨号失败、已经提交但响应丢失、拿到连接后写失败，以及自定义 Transport 的保守判定测试。|
|测量客户端|RPC 失败时仍保留已验证的 mutation outcome，同时将 API 计为失败；不再将已确认的 APPLIED 统一覆写成 UNKNOWN。错误消息只记录有界固定标签或哈希。|真实 TCP/gRPC loopback 的 result+error 账本、合法/缺失确认和有界消息测试。|
|IO 观测|记录 /proc IO、cgroup io.stat、io.pressure 与 block delay 字段，并校验 PID 身份。|离线解析、边界与异常输入测试，以及本轮 MongoDB 连续采样。|

代码位置：[控制器](../internal/store/controller.go)、[发送与取消](../internal/server/route.go)、[Search Transport](../internal/backend/search/transport.go)、[测量客户端](../internal/testutil/testcapacity/client.go)、[资源采样器](../internal/testutil/testresource/main.go)。Lua 继续在单个 Weir 主进程内执行。

本轮 live 没有触发额外的 APPLIED+RPC-error 或明确未发送的 NOT_APPLIED 分支；这些语义改进由针对性测试证明，不能声称已经在本轮 live 中显著减少不确定写。HTTP/2 stream 写 deadline 在当前 Go 1.27.1 下仍可能表现为 Internal reset；记录的 Internal 与固定 reset 标签一致，这些仍计为 API 失败。具体本地标准库依据见 [源码身份与行号](measurements/2026-10-02/refinement-v4/transport-deadline-source.json)。

## 对照条件与统计口径

v3/v4 使用同一个修正后的负载客户端，构建与源码哈希见 [v4 manifest](measurements/2026-10-02/refinement-v4/build-manifest.json)。混合负载为 90% Read/10% Put，约 1KiB 文档，1 秒 caller deadline、有界发送队列、无写重试。CPU 单位为核，RSS 为采样峰值 MiB；数据库连续运行，其缓存会随时间积累。MongoDB 与 ES 的环境不同，不比较两者绝对资源效率。

背压主对照均为同一个数据库进程上的 v3/v4/v4/v3 顺序，每版两轮：2500 次/秒、20 秒预热+120 秒测量，32 业务并发/会话、最大批 8、数据库并发 4、收集 3ms、普通读上限 16KiB、客户端队列 32。数据库内存固定 1536MiB；Weir 2CPU/2304MiB，Weir 资源不随数据库降额而变化。

每个请求按计划到达时间归入 10 秒窗口；纯阶段只使用远离配额变更边界、还留出请求完成余量的整窗，临界窗口另行保留。预热不当作健康测量基线。APPLIED 审计覆盖完整 trial（预热+测量），吞吐/API/drop 表只统计注明的测量期或纯阶段。UNKNOWN 是写入结果的子集，不能与 API 错误相加当成独立失败总数。到达延迟含客户端排队，发送后延迟单独保留在 raw/results。

MongoDB 为 EKS on-demand ARM 节点上同一 MongoDB 8.0.32 进程，WiredTiger 缓存 256MiB、4Gi 普通磁盘 emptyDir。实际 CPU 配额逐段确认 0.5→0.05→0.5 核；变更请求前后时间、Pod/container/PID/start ticks/restart、IO 与实际内存全部归档。第一轮之前统一加入完成余量，42 秒后降额，限额确认后至少 30 秒再恢复。

ES 为独立 Docker ES 8.19.22/Linux ARM64，权威 Java PID 全程一致，实际 CPU 配额 0.5→0.08→0.5 核。ES 变更请求前时间戳缺失，只有确认时间，阶段划分额外排除临界 10 秒窗口，属于保守近似；不能据此报精确的减窗响应时间。ES 阶段 CPU/RSS 使用对应保守资源区间，吞吐使用保留完成余量的到达窗口，二者并非逐请求一一对应。

|目标|可以确认的现状|边界|
|---|---|---|

全量 `go test ./...`、相关包 race、`go vet ./...`、integration helper、取消隔离 10 次 race 和 `git diff --check` 通过；integration helper 不替代本报告的 live 实验。[验证记录与日志](measurements/2026-10-02/refinement-v4/validation/checks.json)。
