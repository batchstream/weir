# ES v2 controller 只读复核

复核对象是此目录两个 `.25→.08→.25 CPU` 重复的冻结 v2 轨迹，未修改生产代码。不能将两次统一解释为“恢复后数据库仍满 CPU”，也不能仅凭窗口未升就认定吞吐没有恢复。

|重复|阶段|DB进程 CPU 核|DB cgroup CPU 核|窗口|hold正值样本|
|---|---|---:|---:|---|---:|
|r000|初始 .25|.2198|.2362|4→1|26/29|
|r000|恢复 .25|.2156|.2331|1→1|46/46|
|r001|初始 .25|.1657|.1834|4→4|14/36|
|r001|恢复 .25|.1622|.1794|1→1|53/53|

r000 初始与恢复 cgroup 消耗分别为 quota 的94.5%和93.3%，恢复阶段225/290个 CFS 周期发生限流。完整10秒窗初始10–20s成功2016.4/s，恢复60–70s与70–80s成功1495.4/s、2490.5/s。这个重复确有接近配额上限的容量压力，不能单独作为尖峰导致恢复饥饿的证明。

r001 初始窗口保持4且没有收缩，但 offered3200/s 并未全部承载：0–10s、10–20s成功3084.8/s、3023.8/s，client drop分别1152、1762。恢复阶段的全部尾部窗口如下，时间从本次负载开始计算，API error与UNKNOWN均为0：

|---|---:|---:|---:|---:|---:|---|
|60–70s|2861.2|3388|18.0|.1681|.1841|完整恢复段内|
|70–80s|3150.6|494|5.6|.1522|.1701|完整恢复段内|
|80–90s|2594.4|6056|83.0|.1825|.2003|跨恢复控制段结束边界|

r001 实际恢复确认在+51.104s，声明30s恢复观察段在+81.104s结束。80–90s仍使用相同 `.25 CPU` quota，但包含该声明段以后的尾部，不能当作完整控制段内窗口；50–60s包含 quota 切换，未用于上述恢复段判断。进程与cgroup数值分别来自权威 Java `/proc` CPU ticks 和 `cpu.stat` 的采样差值。

r001 恢复 cgroup 平均仅消耗 quota 的71.8%；逐采样区间CPU的p10/p50/p90为.158/.174/.199核，88.5%的区间低于.20核。恢复阶段实际执行均值.960ms，优于初始1.483ms；超过10ms的执行仅69/11162（0.62%），初始为158/7605（2.08%）。因此不能将r001的窗口1解释为持续满配额。

恢复 hold在r001全部53个采样中为1，增长事件0、backend拥塞事件0、cooldown样本0；42/53个采样的最新归一化延迟已在 `2×baseline+2ms` 慢阈值内，仍被近期慢证据阻止增长。v2 floor策略允许一条饱和慢成功续期1s hold，缺少可恢复探测的边界，因而存在过于保守的风险。约0.5s采样只能证明hold持续被刷新，无法枚举逐请求慢样本，也不能确认每次续期是否只有单个尖峰。

但r001完整恢复窗3150.6/s已经高于初始完整窗3023.8/s。现有证据支持“floor hold缺少probe边界”，尚无“提高窗口一定改善吞吐”的因果证据，也不支持称该重复吞吐恢复失败。应保留这些反例与丢弃数量；此结论不能外推到其他配额或更低入流，也不能用降rate后的恢复成功证明此参数档的hold机制已改善。
