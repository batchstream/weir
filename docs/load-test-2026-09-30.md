# Local load and database backpressure measurements

These measurements describe the September 30 implementation, where only ordinary
writes were batched. The current scheduler also aggregates Reads, Replace, and
AtomicTransform; Search uses multi-get and compatible bulk writes. The historical
rates below remain historical. The [October 1 report](load-test-2026-10-01.md)
measures the previous and universal-aggregation production binaries against
each other, including a separate congestion recovery experiment.

Write aggregation improved useful throughput in this constrained Elasticsearch
fixture. With common JVM prewarming and a larger direct connection pool, at
4,800 offered writes/s the three-run median was 4,729.95 successful writes/s
through Weir versus 3,005.3 directly, a 57.39% increase. Both paths still
dropped arrivals, so 4,800/s is not a demonstrated lossless SLA capacity.
The 90%-read mixed workload did not improve: at 3,200 offered operations/s,
Weir's median useful rate was 2,513.5/s versus 2,838.65/s directly, 11.45% lower.
Explicit congestion feedback reduced real database rejections by 83.82% and
known failed writes by 86.72%, while trading off more client drops and a 2.66%
lower median useful rate. The evidence therefore supports conditional write
aggregation benefits and database protection, not a general capacity increase.
Run-order improvement remained even after shared prewarming. These short
three-round measurements do not establish steady-state or maximum capacity.

## Scope and measurement contract

The fixture uses Elasticsearch 8.19.22 in local Docker on an arm64 Mac. The
database receives 1,536 MiB memory, a 512 MiB JVM heap and one write thread. Each
trial completes readiness, index setup and corpus seeding with one CPU. A
handshake then lowers the quota to a fixed 0.25 CPU before warmup
and twenty seconds of measurement. The final protocol first runs shared
20-second direct and Weir prewarming phases at 800 ops/s and one database CPU,
then uses twenty seconds of warmup for each measured
trial. Both shared prewarming phases delivered all 16,000 operations without
drops, errors or UNKNOWN outcomes in the write-pool comparison. Earlier groups
used ten seconds of per-trial warmup without shared prewarming and are labelled
separately. Confirmation uses three rounds in AB, BA, AB order. The exploratory
profile used one CPU. Capacity trials use
a write queue of 200. The client receives two CPUs
and 2,048 MiB; Weir receives two additional CPUs and 768 MiB. CPU sets do not
overlap. This holds database resources constant and adds Weir's process cost;
it does not compare equal total application CPU budgets.

Each logical operation reads or writes a deterministic 1 KiB JSON record. The
mixed workload is 90% point reads and 10% inserts through Put; the write workload
is 100% Put to unique keys. There are 1,000 seeded read records. Each trial
recreates the owned index and corpus. Both paths use real-time reads, no write
refresh, one primary, no replicas and request translog durability. Neither path
retries. Every planned write is audited afterwards for payload, presence and
version one; acknowledged application must agree with stored state.
The mapping disables field indexing and the owned data directory uses a 1 GiB
tmpfs. This measures a small cached point-record workload under a CPU quota,
including real Elasticsearch acknowledgement and rejection semantics; it does
not measure persistent disk I/O, application field indexes or search queries.

The direct comparator issues individual native requests and uses four backend
HTTP connections in the matching-limit groups, or 32 in the explicitly tuned
comparison. Weir receives the same open-loop arrivals through four gRPC
connections, shares a backend concurrency ceiling of four and allows physical
write batches of up to 16. Both paths use 64 client workers, a bounded client
queue of 256, a 100 ms arrival-expiry allowance, at most 512 catchup arrivals per
wake and a one-second deadline starting at the planned arrival. Arrivals follow
the fixed schedule; a full client queue produces a recorded drop without
blocking the producer. Search point reads remain individual backend requests. Native bulk
clients that already combine writes are a separate reference, not this direct
comparator.

The following example SLA was chosen for this experiment before confirmation;
the user did not provide an application SLA. Retained counters and histograms
allow a different business SLA to be evaluated afterwards. Capacity means
successful operations from the measurement arrival cohort divided by its
duration, with no client drops, errors or UNKNOWN outcomes and arrival
p95 <= 100 ms and p99 <= 250 ms. Those operations may finish after the cohort's
arrival window, but their original one-second deadline still applies; arrival
latency includes client and Weir queue time. For a 20-second measurement, the
maximum one-second completion tail can inflate cohort goodput by up to 5%
relative to counting through that tail. Final summaries retain actual drain
time and a conservative rate including it; small differences within this bound
are not evidence of a capacity gain. Client CPU usage, scheduling lag,
completed/planned counts and per-kind latencies must also be checked. Pure
timing qualification must deliver every planned arrival without drops, with
lag p99 <= 5 ms; actual-load CPU use must stay below 90% of the client's quota
to support a database capacity conclusion. A rejected operation or an operation
that has not completed is not useful throughput. Successful-operation latency is
reported separately under overload so fast failures cannot appear to improve
latency.

## Prewarmed write comparison with a larger direct pool

This group uses the final common-prewarming/light-observer protocol. The
direct path permits 32 active backend HTTP requests; Weir's configured backend
ceiling is four. This gives the individual-request comparator additional
connection concurrency rather than equating the two limits. Weir's actual
dispatch window was three throughout all three measurement intervals.
During shared JVM prewarming, direct used one backend connection and Weir
retained its ceiling of four; `-pool 1` on the Weir client controls only its
setup/audit HTTP client, not the server's dispatch window. The training phases
exercise both request paths and are not measurements of equal concurrency.

| Offered writes/s | Path | Successful writes/s | Arrival p95, ms | Arrival p99, ms | SLA passing runs |
| ---: | --- | ---: | ---: | ---: | ---: |
| 4,800 | Direct, 32 connections | 3,005.3 (2,202–3,196) | 180 (165–204) | 197 (188–283) | 0/3 |
| 4,800 | Weir, ceiling four | 4,729.95 (4,728.15–4,754.5) | 31 (6–40) | 82 (78–84) | 0/3 |

These are three-run medians and observed ranges, not a confidence interval.
Weir's useful completion rate exceeded direct's in every matched repetition.
The median improvement was 57.39%; including actual completion tails gives
2,977.99/s directly versus 4,729.14/s through Weir, a 58.80% increase. Maximum
tails were 256.91 ms and 3.41 ms. This result persists with the larger direct
pool and after accounting for completion time. It is not a comparison of pool
32 against the earlier pool-four group, whose prewarming protocol differed.
Direct's chronological rates still increased from 2,202 to 3,005.3 to 3,196/s;
common prewarming did not establish stationarity. The conditional pairwise
ordering is retained, without treating its median as a steady-state limit.

Direct dropped 119,934 of 288,000 planned measurement writes (41.644%), versus
3,748 (1.301%) through Weir. There were no transport errors or UNKNOWN outcomes
in warmup or measurement, and the complete version-one payload/presence audit
matched every acknowledged write. Client CPU around the measurement was
0.13–0.28 core out of its two-core quota. Mean Weir physical batch size was
8.60–8.87 operations. Measured Elasticsearch rejection and Weir window-decrease
counters were zero: the benefit here is write aggregation, not demonstrated
congestion-feedback action. All runs failed the lossless example SLA because
of client drops, even though Weir's completed-operation p95/p99 passed its
latency thresholds. An application already using native bulk operations remains
an unmeasured comparator.
The earlier helper used a 90/10 timing-only construction probe even for this
100%-write business group. That qualification did not cover the exact
construction ratio. Actual producer wake p99 was 1.4–1.5 ms in these runs,
and the low measured client CPU provides separate evidence against generator
CPU saturation. A later helper fixes only the probe's `WriteEvery` parameter;
the pressure group's 48,000-write timing qualification uses the exact ratio,
with the distinct binary hashes retained. This difference is disclosed rather
than treating the old probe as identical to the business workload.

## Prewarmed mixed-load confirmation

The final mixed comparison uses the same common JVM training and twenty-second
per-trial warmup as the tuned write experiment, with both direct and Weir
backend ceilings set to four. Its timing-only qualification used the actual
90/10 construction ratio and delivered 32,000/32,000 arrivals without drops,
with lag p99 of 1.6 ms. Client CPU around the measurement was 0.16–0.21 core
out of its two-core quota.

| Offered ops/s | Path | Successful ops/s | Arrival p95, ms | Arrival p99, ms | SLA passing runs |
| ---: | --- | ---: | ---: | ---: | ---: |
| 3,200 | Direct | 2,838.65 (2,315.7–3,032.5) | 179 (119–197) | 258 (198–281) | 0/3 |
| 3,200 | Weir | 2,513.5 (2,362.6–2,682.9) | 198 (168–282) | 301 (210–441) | 0/3 |

The table gives medians and observed ranges. Direct dropped 28,263 of 192,000
planned measurement arrivals; Weir dropped 40,820. All completed measurement
operations succeeded and there were no warmup/measurement errors or UNKNOWN
outcomes; every planned write passed the complete audit. The median useful
rate was 11.45% lower through Weir. Including actual completion tails gives
2,838.35/s directly and 2,501.47/s through Weir, preserving the negative
direction. Maximum tails were 4.75 ms and 573.53 ms, respectively. One matched
round favored Weir; the other two favored direct. This is evidence against a
general mixed-load benefit in this fixture, not a claim that every possible
read-heavy workload has this exact regression.

No explicit backend write rejections occurred. Weir's observed window stayed
at four, with zero decrease/cooldown observations and mean physical batch size
1.077. Point reads are not batched. Each Weir physical execution first performs
an index-capability qualification GET before the record GET or bulk write;
the direct point-read comparator only needs the record GET. This extra
qualification request provides a concrete source of request overhead for the
read-heavy workload. It enforces safety semantics and was not removed or cached
to improve the benchmark. Latency-only overload did not activate the explicit
congestion controller.

## Explicit database congestion feedback and its cost

The causal experiment uses the same test server assembly for both variants,
with the real Elasticsearch write queue reduced to two, a configured backend
ceiling of 32 and batches of up to 16. It retains the common-prewarming,
twenty-second warmup/measurement and light-observer protocol. Shared training
uses one direct HTTP connection and the adaptive server's ceiling of 32. The
control changes only confirmed `Congested` feedback to `Neutral`; healthy
additive growth, batching, queues and connection limits remain enabled. There
is no production "backpressure off" setting and this control does not configure
a fixed dispatch window.

The backend generates actual write-queue rejections; no latency, response code
or feedback is injected. Three paired rounds at 4,800 offered writes/s give:

| Measurement across three 96,000-write cohorts | Adaptive feedback | Feedback suppressed |
| --- | ---: | ---: |
| Successful writes, total | 264,956 / 288,000 | 268,777 / 288,000 |
| Successful writes/s, median (range) | 4,527.4 (4,149.4–4,571) | 4,651 (4,073.7–4,714.15) |
| Known failed logical writes (`UNAVAILABLE`) | 79 | 595 |
| Client queue drops | 22,965 | 18,628 |
| Sampled physical Elasticsearch write rejections | 11 | 68 |
| Window decreases | 11 | 0 |
| Actual sampled window range | 1–3 | 3–3 |
| Successful-arrival p99, median (range), ms | 194 (184–201) | 123 (92–184) |
| UNKNOWN application outcomes | 0 | 0 |

The adaptive path reduced sampled database rejections by 83.82% and known
failed logical writes by 86.72%. Its measured decrease counts were 4, 3 and 4,
with healthy additive increases of 9, 6 and 7 during overload and cooldown
visible in 1–2 samples per run. The control suppressed 37, 12 and 20 congestion
signals and had no decreases. Its actual sampled window stayed at three;
the ceiling of 32 was not the exercised concurrency. This chain supports a
causal effect from real backend rejection through controller reduction to
fewer backend rejections. Logical failure counts differ from physical
rejection counts because a rejected batch contains multiple logical writes;
the approximately 2 Hz counter sampling also omits partial edge intervals.

The protection has a measurable cost. Adaptive useful throughput was 2.66%
lower by the three-run median, or 1.42% lower when pooling all successful
cohort operations. It dropped more arrivals and had worse successful-operation
tail latency. Counting actual completion tails changes the medians to
4,526.89/s adaptive and 4,650.27/s control, preserving the ordering. Both paths
failed the lossless SLA in all repetitions. These measurements demonstrate
database protection, not a universal throughput or latency improvement.

Recovery immediately reduces arrivals to 100 writes/s for twenty seconds,
using the same client process, Store, runtime, database, index and CPU quota.
No setup, reset or retry occurs between overload and recovery. Recovery starts
20.02–20.31 ms after the pressure workers finish, or 22.57–25.70 ms after the
nominal pressure window. Adaptive completed all 6,000 recovery writes without
drops or failures and passed the example SLA in every run; arrival p99 was
29–66 ms. Control completed 5,994/6,000, with 5, 0 and 1 known failures, no
drops and SLA success in one of three runs. The sampled recovery backend
rejections and suppressed signals were also 5, 0 and 1 for the control and
zero for adaptive. The two separate audits per run cover all 192,000 planned
warmup/measurement writes and all 2,000 recovery writes. Every acknowledged
write has the expected payload and version one, every known-not-applied or
unstarted write is absent, and all twelve audits succeeded with no UNKNOWN
application outcomes or replay.

[full histogram summary](measurements/2026-09-30/backpressure-full-summary.json.gz)
and [raw manifest](measurements/2026-09-30/backpressure-raw-manifest.json)

Client identities and Weir process start times stayed unchanged within each

## Changes and validation

Investigation found that complete Native backend overload responses lost their
congestion feedback. The change preserves the original native response and
completion evidence while supplying congestion feedback for complete Search
HTTP 429/503 responses and complete MongoDB command errors already classified
as congestion. Incomplete output remains neutral. Search bulk item errors
inside an HTTP 200 response remain opaque and are not parsed by this change.

Focused tests cover raw response preservation, single execution and incomplete
delivery. The real MongoDB Native overload regression also executed on an
isolated EKS MongoDB 8.0.32 single-primary fixture:
`TestMongoNativeRealErrorsBoundsAndReplyLoss/overload` passed in 0.13 seconds.
It uses MongoDB's `failCommand` with code 16500 to verify the real driver,
complete BSON reply digest, one command execution, congestion feedback and
completion contract. This is a real-backend mechanism regression with an
injected command error, not a MongoDB natural-load experiment. The
[execution/cleanup receipt](measurements/2026-09-30/mongo-native-integration.json)
and [test log](measurements/2026-09-30/mongo-native-integration.log) retain the
successful execution; the owned namespace was deleted and confirmed absent,
and this attempt used no port-forward. Earlier blocked/failed fixture attempts
were cleaned and are preserved locally rather than counted as successful tests.

Local validation passed with Go 1.27.1 and cached dependencies: default
`go test -count=1 -timeout=180s ./...`, the full default race suite, vet with
and without `integration`, and the integration-tag helper suite including
race detection. Vet found a sampler context not cancelled on a load-delay
early return; the helper now defers cancellation immediately after creating
the context, and integration vet/helper race checks passed after the fix.
This does not change the normal measured path, which already stopped and
joined its sampler. Both ordinary and optimized Python suites passed. The
four CI-gated real Go completion consumer cases were also exercised using a
locally compiled integration helper test binary; optimized execution retains
the two expected legacy/debug calibration skips. Formatting, Python compilation
and whitespace checks passed. The [local validation receipt](measurements/2026-09-30/validation-summary.json)
records commands and coverage, including the follow-up completion paths rather
than counting their initial missing-binary skips as execution.

## Reproducing the measurements

Use the current source with Go 1.27.1 and Docker's linux/arm64 engine exposing
at least five CPU IDs. The recorded engine exposes eight CPUs. The fixture
requires the recorded Elasticsearch 8.19.22 image, SHA-256
`a1cc67962f24c058c854acc6aab0d0adaefefc945c0bfaaebb52aba6129de160`.
The following builds do not change Go's persistent settings or contact module
registries; dependencies must already be cached. The destination for each
runner invocation must not already exist.

```sh
WEIR_GO_ROOT="$(go env GOROOT)"
"$WEIR_GO_ROOT/bin/go" version
mkdir -p .testdata/reproduce-20260930
env GOROOT="$WEIR_GO_ROOT" GOENV=off GOWORK=off GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  "$WEIR_GO_ROOT/bin/go" build -tags=integration -trimpath -buildvcs=false \
  -o .testdata/reproduce-20260930/client ./internal/testutil/testcapacity
env GOROOT="$WEIR_GO_ROOT" GOENV=off GOWORK=off GOTOOLCHAIN=local GOPROXY=off GOSUMDB=off CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  "$WEIR_GO_ROOT/bin/go" build -trimpath -buildvcs=false \
  -o .testdata/reproduce-20260930/weir ./cmd/weir
python3 scripts/compare-load.py \
  --client .testdata/reproduce-20260930/client --weir .testdata/reproduce-20260930/weir \
  --output .testdata/reproduce-20260930/write --rates 4800 --write-every 1 \
  --modes direct,weir --repetitions 3 --warm 20 --seconds 20 --pool 4 --direct-pool 32 \
  --batch-operations 16 --db-cpu 0.25 --db-queue 200 --prewarm
```

The runner records binary hashes, actual image identity, limits, per-run
samples, planned-arrival cohorts and correctness audits. It removes its
labelled containers, imported binary image and network in a `finally` block,
including failed invocations, and records the before/after Docker inventory.
The raw files remain under the selected local evidence directory. Committed
compact summaries retain every phase's counts and quantiles; the accompanying
gzip files retain all histogram buckets, and manifests hash the local source
files. Earlier full-hash-observer data is historical evidence and cannot be
reproduced by the lighter observer as an identical protocol.

## Limits and cleanup

These local, short-duration, constrained Elasticsearch measurements do not
establish production or EKS capacity, MongoDB/OpenSearch throughput, long-run
leak freedom, search/query workload capacity or a globally coordinated database
limit. Three repetitions give observed variation, not a statistically estimated
