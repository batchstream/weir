# Universal aggregation and congestion recovery measurements

The universal scheduler was merged in [PR #7](https://github.com/batchstream/weir/pull/7)
before these measurements. Relative to the previous production implementation,
the three-pair median successful rate for 90% Read / 10% Put at 3,200 offered
operations/s increased from 2,662.27 to 3,200/s, or 20.20%. Successful arrival
p95 decreased from 170 to 4.2 ms. Pure Put throughput at 4,800 offered writes/s
was effectively unchanged: 4,685.70 to 4,714.87/s, or 0.62%.

These are local, constrained Elasticsearch results for Read and Put. They do
not establish production capacity, MongoDB performance, or a performance gain
for Replace, AtomicTransform, Native or Scan. Correctness integration tests
cover those operations separately. The
[September 30 report](load-test-2026-09-30.md) compares a different historical
implementation against direct HTTP; its numbers are not a matched baseline
for this architecture change.

Source revisions are declarations from the builder, not inferred from a hash.
The harness hashes the same byte buffers it imports into the binary image.
The measured binary paths were immutable throughout each group. Explicit
`--client-source`, `--weir-source` and `--baseline-source` options allow the
same older binaries to be used from a later harness checkout.

All binaries use Go 1.27.1, linux/arm64, CGO disabled, `-trimpath` and
`-buildvcs=false`. The fixture image is Elasticsearch 8.19.22,
`sha256:a1cc67962f24c058c854acc6aab0d0adaefefc945c0bfaaebb52aba6129de160`.
Docker 29.7.2 runs an eight-CPU aarch64 VM with 8,319,770,624 bytes of memory
on an arm64 Mac. The database has a 0.25 CPU quota on CPU 0, 1,536 MiB memory,
a 512 MiB JVM heap, and one write thread. Weir has two CPUs on CPUs 3–4 and
768 MiB; the client has two CPUs on CPUs 1–2 and 2,048 MiB. CPU sets do not
overlap. The write queue is 200 for the architecture comparison and two for
explicit congestion experiments.

Each operation uses a deterministic 1 KiB JSON point record. Mixed load reads
1,000 seeded keys and creates unique records through Put. The index has one
primary, no replicas, field indexing disabled, no write refresh, request
translog durability and a task-owned 1 GiB tmpfs data directory. The test
includes real Elasticsearch acknowledgements and rejections, but does not
measure persistent disk I/O, application indexes or search queries. Neither
the client nor the ordinary-write backend retries. Audits check the presence,
payload and version one of every planned write, including warmup and recovery.
Acknowledged application must match persisted state.

The client uses fixed open-loop arrivals, 64 workers, a bounded queue of 256,
100 ms arrival expiry, at most 512 catchup arrivals per wake, and a one-second
deadline measured from the planned arrival. It uses four gRPC connections;
each server connection allows eight active unary streams. Thus the stress
test's configured backend ceiling of 32 is a ceiling, not a forced dispatch
window of 32. Architecture trials use a ceiling of four. Both allow up to 16
operations per physical batch.

All paired groups first train the common JVM through direct HTTP and both
production paths, each for 20 seconds at 800 operations/s and **one database
CPU**. The harness explicitly restores that quota for every training path.
It then lowers the quota to 0.25 for each trial. The first groups use 10 seconds
of per-trial warmup; the longer cooldown confirmation uses 20 seconds. Each
pair alternates its execution order: AB, BA, AB, and BA for the fourth pair.
Every trial recreates its owned index and corpus. Shared prewarming reduces
but does not eliminate run-order and JVM variability.

Successful operations from the measurement arrival cohort divided by nominal
measurement duration are reported as successful operations/s. Completion can
extend beyond that arrival interval, bounded by the original deadline. Raw
receipts retain actual drain time and the conservative rate including it.
Successful arrival latency includes client and Weir queueing; failed operations
do not enter successful latency histograms. Quantiles are histogram bucket
upper bounds, not exact individual timings or confidence intervals. Client
queue drops occur before an RPC and are included in total offered losses
alongside known API failures. Timing-only qualification uses the actual
construction ratio and must produce every scheduled arrival with zero drops
and wake p99 at most 5 ms.

## Matched architecture comparison

Each row reports three-run medians with observed ranges. Measurement duration
is 30 seconds per run. All measurement operations that reached an RPC succeeded;
there were no measured API failures, UNKNOWN outcomes or backend write
rejections. Every write audit matched.

| Workload and offered rate | Path | Successful ops/s | Successful arrival p95, ms | Client drops, total |
| --- | --- | ---: | ---: | ---: |
| 90% Read / 10% Put, 800/s | Previous | 800 (800–800) | 21 (2.6–92) | 0 / 72,000 |
| 90% Read / 10% Put, 800/s | Universal | 800 (800–800) | 3.4 (3.3–4) | 0 / 72,000 |
| 90% Read / 10% Put, 3,200/s | Previous | 2,662.27 (2,654.13–2,692.73) | 170 (165–172) | 47,726 / 288,000 |
| 90% Read / 10% Put, 3,200/s | Universal | 3,200 (3,194.17–3,200) | 4.2 (4.1–4.2) | 175 / 288,000 |
| 100% Put, 4,800/s | Previous | 4,685.70 (4,396.33–4,726.43) | 40 (16–101) | 17,746 / 432,000 |
| 100% Put, 4,800/s | Universal | 4,714.87 (4,605.70–4,736.70) | 23 (7.3–67) | 10,282 / 432,000 |

At 3,200/s, the previous path's nine ten-second windows delivered
2,496–2,804 successful operations/s with p95 149–200 ms. Universal aggregation
delivered 3,182.5–3,200/s with p95 4.0–9.8 ms. The benefit appears in every
paired repetition and throughout the measurement windows. The median p99
decreased from 280 to 14 ms. Client drop fraction decreased from 16.57% to
0.0608%; the first universal run had a brief 175-operation client queue
overflow, so the group does not demonstrate lossless capacity at 3,200/s.

The median physical batch grew from 1.077 to 5.926 operations, and median
scheduler executions decreased from 72,647 to 15,725 per observed measurement
interval. These executions are **not a count of backend HTTP calls**: a Search
execution can include capability inspection, multi-get and bulk phases.
Observed database CPU decreased from approximately 0.249–0.251 to
0.140–0.155 core; recorded JVM GC time decreased from 594–822 to 55–58 ms per
measurement. The database's exact cgroup throttled time was not captured.
Producer wake qualification passed, measured client CPU remained comfortably
below its quota, and the client cgroup recorded no throttling.

At 800/s both versions delivered all arrivals. Early previous-version latency
outliers disappear as the JVM settles. The final pair's p95 was 2.6 versus
3.3 ms, showing approximately 0.7 ms collection overhead. The low-load median
does not establish a steady-state latency benefit. For pure Put both versions
already form batches of roughly nine operations. The 0.62% median throughput
difference is small relative to run-order variability, and the final pair
differs by only 0.22%; a meaningful pure-write capacity increase is not claimed.

## Congestion feedback and its cost

The first stress experiment uses the merged architecture in an integration
assembly with two modes. `adaptive` preserves production feedback; `control`
changes only confirmed adapter `Congested` feedback to `Neutral`. Healthy
growth, admission limits, batching, deadlines and configured ceiling 32 are
otherwise identical. Control is neither fixed concurrency 32 nor an absence
of all backpressure. Each of three pairs measures 20 seconds at 4,800 Put/s
with a database write queue of two, followed by 20 seconds at 100 Put/s.

| Feedback mode | Successful writes/s, median | Successful p95, median ms | Backend rejection events, median | Known failed writes, median | Client drops, total |
| --- | ---: | ---: | ---: | ---: | ---: |
| Adaptive | 4,484.75 | 56 | 4 | 30 | 39,408 |
| Congestion signal suppressed | 4,717.35 | 29 | 16 | 133 | 5,268 |

Feedback reduces median backend rejection events by 75% and median known
failed writes by 77.4%. Across all measured cohorts, known failures are
83/248,592 started writes (0.0334%) versus 508/282,732 (0.1797%). However,
adaptive median goodput is 4.93% lower and its total offered losses are
39,491/288,000 (13.71%) versus 5,776/288,000 (2.01%). One early adaptive run
accounts for 29,429 drops; the remaining two also have more drops than their
paired controls. Fewer backend rejections alone does not mean better overall
efficiency.

The original 100–300 ms cooldown suspends new dispatch after confirmed
congestion. At 4,800 arrivals/s that interval admits 480–1,440 new arrivals
before dispatch resumes, compared with a client queue of 256 and a 100 ms
arrival-expiry allowance. This provides a concrete reason to test a shorter,
still bounded cooldown. The candidate changes only that jittered interval to
20–60 ms; multiplicative decrease, floor one, epoch protection, healthy growth
and all admission/memory/concurrency ceilings remain unchanged.

Original adaptive recovery completes 5,999/6,000 scheduled writes; the
suppressed-feedback control completes 5,992/6,000. There are no recovery drops
or UNKNOWN outcomes, but there are respectively one and eight known backend
failures. Recovery begins **after** outstanding pressure workers drain, so it
does not measure an instantaneous arrival-rate switch. Actual pressure drain
is 3.6–25.9 ms for adaptive versus 3.2–261.4 ms for control; recovery-start
delay is 24.1–46.5 versus 23.5–281.5 ms. Audits happen after recovery.

## Short-cooldown experiment

This experiment compares production binaries at `3ada0fd` and `d95acc6`, using
the same candidate client for both. The first group uses three alternating
pairs, 10-second warmup and 20-second measurement. All six recovery probes
deliver 2,000/2,000 scheduled writes, with zero failures, drops, UNKNOWN or
backend rejection events. Audits match and sampled limits remain respected.

| Pair | Original successful writes/s | Short cooldown writes/s | Original total loss | Short cooldown total loss |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 3,900.15 | 4,476.15 | 17,997 | 6,477 |
| 2 | 4,689.95 | 4,391.00 | 2,201 | 8,180 |
| 3 | 4,533.20 | 4,726.50 | 5,336 | 1,470 |

The candidate improves two pairs and materially regresses one. Aggregate
successful operations increase by 3.58% and total losses decrease from 25,534
to 16,127 (36.84%). Combining histogram counts gives p95 102 to 59 ms.
Nevertheless, per-run median goodput decreases 1.26%, from 4,533.20 to
4,476.15/s, and per-run median p95 increases from 67 to 83 ms. These results
alone do not establish a stable performance improvement. Known failures rise
slightly, 71/262,537 started writes (0.0270%) to 84/271,957 (0.0309%), despite
ten physical backend rejection events for each version. Per-item failures
within a rejected bulk are correlated, not independent rejection events.

The longer confirmation increases per-trial warmup to 20 seconds and
measurement to 30 seconds, with four balanced AB/BA pairs. All other fixture
settings and binary hashes remain the same:

| Pair and order | Original successful writes/s | Short cooldown writes/s | Original total loss | Short cooldown total loss | Original / short p95, ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1, original then short | 4,390.37 | 4,758.97 | 12,289 | 1,231 | 105 / 20 |
| 2, short then original | 4,681.63 | 4,612.63 | 3,551 | 5,621 | 16 / 57 |
| 3, original then short | 4,573.57 | 4,769.20 | 6,793 | 924 | 29 / 6.4 |
| 4, short then original | 4,649.23 | 4,674.47 | 4,523 | 3,766 | 18 / 26 |

The positive figures are retained: median successful rate increases from
4,611.40 to 4,716.72/s (2.28%), aggregate successful count increases 2.85%,
and total losses decrease from 27,156 to 11,542 (57.50%). Combining histogram
counts gives p95 41 to 23 ms. Known failures are 136/548,980 started writes
(0.02477%) versus 124/564,582 (0.02196%); physical backend rejection events
are 16 versus 14, with a per-run median of 3.5 for both versions.

However, median p95 is essentially flat, 23.5 versus 23 ms. The two
original-first pairs favor short cooldown by 8.40% and 4.28%; the two
short-first pairs show -1.47% and +0.54%. The last pair's p95 worsens from
18 to 26 ms. Across both production comparison groups, the second
chronological run has higher goodput in six of seven pairs. Only two of four
longer pairs improve goodput, total loss **and** p95 together, both in the
original-first order. This remains evidence of order/state confounding,
rather than a demonstrated stable benefit from changing cooldown.

**The production cooldown change was reverted.** The final implementation
retains 100–300 ms. A shorter timer could increase request attempts during
sustained immediate rejections; the measured positives do not justify that
policy change when causal attribution remains uncertain. The benchmark's
100 ms arrival-expiry allowance is not a requirement that all RPC deadlines
be 100 ms; their lifetime here is one second. No separate application deadline
policy was supplied. The candidate binaries and all trials remain recorded
so this decision is reviewable.

Longer recovery completes 7,998/8,000 original and 8,000/8,000 candidate
writes. The original has two known UNAVAILABLE failures in separate recovery
cohorts, each accompanied by a backend rejection and accepted window
decrease. There are no recovery drops or UNKNOWN outcomes, and all payload
and version audits match. One candidate recovery has p95 41 ms, so no
uniform recovery-latency improvement is claimed. Pressure completion tails
are 2.0–4.8 ms and recovery starts 22.1–25.2 ms after nominal pressure end.

In both production stress groups, sampled dispatch windows remain between
one and three despite a configured ceiling of 32. Pending entries reach at
most 32, retained entries at most 32, and process RSS approximately
28.0–29.8 MB. There are no sampled configured concurrency, entry or byte-limit
violations. Half-second sampling can miss the shorter cooldown itself;
window-change counters and controller tests provide separate evidence that
feedback operates. In-flight executions may temporarily exceed the newly
reduced dynamic window while they drain, without exceeding the configured
ceiling. Epoch protection prevents old results from renewing cooldown.

All disposable benchmark containers, networks and imported binary images
are removed. Non-default Docker inventories are restored. Exact full
inventory restoration is false in the cooldown groups because Docker's
default bridge ID changed; the cleanup receipts disclose this exception.
It does not leave any task-owned resources running.

## Validation

Default Go tests, race tests and both ordinary/integration vet checks pass.
Real plaintext MongoDB, Elasticsearch and OpenSearch tests cover mixed
batching, cancellation, per-item results, acknowledgement uncertainty and
public RPCs. The repaired three-process public smoke exercises Read, Mutate,
Bulk, Native and Scan through two forwarding peers, checks terminal counts
and persisted values, then verifies both backends recover after each peer
process is replaced. It passes against MongoDB with both Search products.
No separate Lua worker process is introduced.

The paired harness has offline regressions for common resources/prewarming,
alternating order, explicit source declarations and hashes that remain correct
if binary paths are overwritten during startup. Focused tests pass both
normally and with Python optimization. Legacy ordinary-Python-only fixture
tests retain their explicit optimization refusal; their optimized test skips
do not constitute coverage of those fixtures.

synthetic and all endpoints are task-owned loopback/internal Docker addresses.

Build `./cmd/weir` from each declared revision and the common integration
client from `./internal/testutil/testcapacity`. The paired helper requires
explicit baseline source provenance, common prewarming and at least three
repetitions. Example architecture comparison, with previously built binaries:

```sh
python3 scripts/compare-load.py \
  --client .testdata/universal-aggregation/client \
  --client-source 3ada0fd8921f3f7c536d99e7e31279c51d6e62e2 \
  --baseline-weir .testdata/universal-aggregation/weir-baseline \
  --baseline-source 4a43a6328d11809e752d8a4751e85eea50687e6c \
  --weir .testdata/universal-aggregation/weir-current \
  --weir-source 3ada0fd8921f3f7c536d99e7e31279c51d6e62e2 \
  --output .testdata/universal-aggregation/mixed-paired \
  --rates 800,3200 --write-every 10 --modes baseline,weir \
  --repetitions 3 --warm 10 --seconds 30 --pool 4 \
  --db-cpu 0.25 --db-queue 200 --prewarm
```

Use `--rates 4800 --write-every 1` for pure Put. The congestion-suppression
assembly uses `--modes adaptive,control --pool 32 --db-queue 2 --seconds 20
--recovery-rate 100 --recovery-seconds 20` without a baseline binary. The
production cooldown comparison uses the `3ada0fd` baseline, `d95acc6` candidate
and their common candidate client declared with `--client-source d95acc6`,
`--modes baseline,weir --pool 32
--db-queue 2 --rates 4800 --write-every 1 --recovery-rate 100
--recovery-seconds 20`. Longer confirmation additionally uses
`--warm 20 --seconds 30 --repetitions 4`.
