# Weir 数据库减载、连接集中与背压验证（2026-10-02）

> v2 中间版本记录。v3 修复健康尾延迟阻碍恢复的问题后，最终结论以独立的 v3 报告为准。

本轮对生产执行路径进行了重构，并使用真实 MongoDB 和 Elasticsearch 验证。本记录版本称为 v2（中间版本）；中间版本 v1 的结果和失败反例单独保存，不能当成最终版本数据。基线是改动前的 `614eb443e298ffc531507a32743b15f5a4baea00`，构建身份见 [v2 manifest](measurements/2026-10-02/build-manifest-v2.json)。

## 改动及其目的

- MongoDB 同一批内只做一次 namespace 资格检查，随后执行读和写；单个 `_id` 直接使用等值查询，多个 ID 使用 `$in`。不跨批缓存权限或 collection 状态。
- 普通 Record Read 新增 `local.max_read_size`，范围 1KiB–2MiB，默认 2MiB。已知小文档可使用较小的读结果预算，释放同时执行的预算，并允许 ES `_mget` 合并更多文档；超限读返回 `RESOURCE_EXHAUSTED`。该参数不改变写入、Scan、Native 或 Lua 的文档语义。
- 新增 `local.batch_collect`，范围 0–10ms，默认 1ms。选择收集窗口时同时考察数据库 CPU、吞吐和延迟，不能只以单次请求延迟作为目标。
- ES JSON 校验与 bulk 回复解析减少重复解码和分配。保持 UTF-8、转义、重复键、深度与节点数检查；差分 fuzz 未发现语义差异。
- 执行调度允许独立且预算足够的请求越过暂时被工作内存阻塞的请求，保持会话与键的顺序约束。
- 背压从只识别显式容量错误，扩展为识别成功但持续变慢的批次。按目标、操作类型、批大小与输入大小分别预热基线，避免把更大批次或 Lua 计算当成数据库退化。出现队列压力且同类批次持续变慢时降低窗口；近期慢样本会阻止快速恢复，避免 CPU 配额的快慢交替导致窗口立即回升。调用方取消不会参与延迟学习。

所有执行仍在一个 Weir 进程内，Lua 在主进程内运行。

## 性能对照方法

数据库固定为 **0.25 CPU、1536MiB 内存上限**。Weir 使用 **2 CPU**；第一组吞吐调优参数是 64 个业务并发、64 个会话、4608MiB 配置内存预算、数据库并发 2、最大批 32、收集 5ms、普通读上限 16KiB；MongoDB 另有独立 10ms 混合负载配对组。这个内存值是保守的配置预算，并非实际 RSS。直接路径使用相同负载客户端、64 并发、连接池 4。

负载是约 1KiB 文档、1000 个预置读键，混合场景为 90% 读/10% 写，另有纯写场景；每轮预热 10 秒、测量 20 秒，800 和 3200 次/秒，三次重复并交替路径顺序。客户端按计划到达时间计时、最多保留 256 个待执行请求、排队过期 100ms、请求 deadline 1 秒，无自动重试。成功吞吐、发出前的 client drop、API 失败与 UNKNOWN 分开统计。

MongoDB 8.0.32 在隔离的 EKS 临时 Pod 内运行；ES 8.19.22 在临时 Docker 夹具内运行。两者独立测试，不能据此比较不同数据库的绝对性能。CPU 来自被测进程的 `/proc` 差分，单位是核；RSS 是测量窗内最大采样值，再对三轮取中位数。数据库进程连续运行，RSS 包含累积缓存，不能把随轮次变化的 RSS 当成代码造成的内存节省。

每轮生成的写入都有独立标识。测试结束后验证所有 APPLIED 写入的真实 BSON/JSON 内容；UNKNOWN 单独检查实际落库状态，未确认的写入不会被计为成功。

## 连接集中

使用 1 个和 16 个真实业务进程，以相同总到达率执行只读请求；另测这些进程通过同一个 Weir。观察器只读取数据库进程的 socket inode 与 TCP 表，不额外打开数据库连接。测量业务流量期、业务客户端关闭后的空闲期，以及停止 Weir 后连接回到基线的情况。

MongoDB 最终 v2 使用相同 200/s、4000 次读、1/16 个实际业务进程。四格全部成功、无 client drop/API 失败/admission 拒绝/OOM。

|路径|实际数据库连接|DB CPU 核|Weir CPU 核|DB RSS MiB|Weir RSS MiB|
|---|---:|---:|---:|---:|---:|
|1 进程直连|5|0.0532|—|328.9|—|
|16 进程直连|32|0.0542|—|327.7|—|
|1 进程 → 单 Weir|2|0.0763|0.2347|328.1|24.6|
|16 进程 → 单 Weir|5|0.0768|0.1605|329.4|28.1|

**16 进程的实测数据库连接从 32 降至 5，减少 84.4%。** 连接包含驱动监控；不能把 pool4 的理论总上限 80 当成该格的实际连接数。Weir 的 raw owner 峰值均不超过池加生命周期上限 5，停止后 acquired/released 平衡，数据库连接回到最初的 0。

这个低速同步读场景数据库 CPU 上升，平均批仅约 1.04，不能将连接集中误报为 CPU 减载。两个单进程格遍历全部 1000 个读键四轮；16 进程格共同覆盖 260 个读键，但每一条返回值都验证完整 1KiB BSON。

ES 较早版本的独立连接矩阵在 200/s 全部成功时，16 进程直连实测中位数 16 条（范围16–32），单 Weir 4 条；800/s 全部成功的双 Weir 为 8 条，对照直连 64 条。800/s 单 Weir 的较早版本仍有会话拒绝，已保留失败，不能当成最终 v2 的满吞吐证明。HTTP 同样使用 TCP 连接池，因此 ES 也存在连接集中的收益。

完整版本身份、四格 MongoDB 原始数据、较早 ES 成功与失败格、停止回收和清理凭证见 [连接验证报告](measurements/2026-10-02/connection-goals/connection-findings.md)、[汇总](measurements/2026-10-02/connection-goals/connection-results.json) 与 [SHA256](measurements/2026-10-02/connection-goals/sha256.json)。

共享连接池可以让业务进程数增长时数据库连接数保持有界。每个 LocalStore 有独立池；增加 Weir 副本仍会增加数据库连接和执行并发。已增加 [HPA 示例与连接预算说明](../deploy/kubernetes/scaling.md)，需要把副本、滚动更新和终止中的 Pod 都计入预算。本轮未部署 HPA，也没有以耗尽真实数据库连接上限作为验收；验证的是实际连接集中和关闭回收。

连接探针会同步发送同一个读键，不能拿其合批率推断一般读写吞吐。16 个进程每个 8 个 worker 可以产生 128 个在途 RPC，32/64 个会话仍可能在 CPU 尚有余量时触发会话 admission。CPU HPA 不会自动处理这种限制，增加副本还需要客户端分配会话。

## 真实背压与恢复

连续运行的数据库进程在测量中降低 CPU 配额再恢复，保留实际 `cpu.max`、进程启动标识、窗口、延迟基线、恢复 hold、CPU/RSS 和写入审计。背压验证使用最大批 8、数据库并发 4、32 个业务并发/会话、客户端队列 32、收集 3ms、读上限 16KiB；这是为产生可观测的持续在途压力而设定的独立场景，不与吞吐参数混为一谈。

MongoDB 两次最终试验：0.5 核 → 0.05 核 → 0.5 核，数据库保持同一 PID 与启动标识，无重启/OOM。两次都从窗口 4 收缩到 1，低配额的保守观测区间始终保持 1；恢复后窗口 2 已足以回到约 2500/s。恢复期间各有一次短暂 2→1→2，不声称完全无振荡或已恢复到配置上限 4。

|1|健康|预热2500|0.351|1.204|310.0|24.8|4–4|

|2|恢复|2500.0/2455.3/2500.0|0.327|1.168|330.0|25.3|1–2|

受限/恢复吞吐仅使用完全落在实际配额确认后区间内的 10s 窗，过渡窗口保留但不混入比较；健康吞吐为完整 20s 预热平均。两次最终测量合计 450000 个计划请求中，260941 成功、189059 在客户端队列中被丢弃，API 失败和 UNKNOWN 均为 0；所有 **36137 笔 APPLIED 写入**（含预热）全部真实存在。受限阶段并非全部输入成功：该配置以有限排队和降低并发保护数据库。

旧版本的两次组合对照窗口始终为 4，API 失败 115、UNKNOWN 13；其 33383 笔 APPLIED 全部存在，另有 11 笔 UNKNOWN 实际落库。旧版本使用默认 1ms/2MiB，新版本使用 3ms/16KiB；两组均 batch8/pool4/queue32/worker32、同一 v2 客户端。因此失败差异包含实现与调参的组合效果，不能单独归因于延迟控制器。成功慢回复触发的窗口收缩及恢复才是本轮背压的直接证据。

完整表格、所有 drop/失败/UNKNOWN、actual quota、hold、控制事件、v1 反例和原始归档见 [MongoDB 背压报告](measurements/2026-10-02/backpressure-goals/mongodb/report.md) 与 [SHA256](measurements/2026-10-02/backpressure-goals/mongodb/SHA256SUMS)。

ES v2 降配试验及健康余量试验暴露了少量尾延迟反复续期恢复 hold 的问题；该版本仅作中间证据，详见 es-v2-quota-overloaded 和 es-v2-healthy-pilots。

保护能力是将数据库在途工作保持在有界窗口内，并在压力持续时减少并发。无法承诺无限输入均成功；上游必须处理 admission、超时和队列丢弃。数据库 CPU 满额本身不直接触发该控制器，控制器观察的是完成时间、显式容量反馈和队列压力。没有有效饱和或没有预热过的同类样本时，检测能力有限。

## 验证与证据边界

默认 `go test ./...`、store/app/两种后端/execution 的 race 测试与 vet 已通过；integration capacity helper 测试、Python 工具测试 normal/优化模式各 122 项通过，分别跳过 4/31 项，其后 ES PID 仪表修正的 14 项 focused 测试在 normal/优化模式均通过，两种负载工具共 20 项测试均无跳过。完整日志和既有 Go 验证记录见 [validation.json](measurements/2026-10-02/validation.json)。普通默认测试不访问生产或启动真实负载夹具。

中间试验暴露了两类问题并保留证据：成功慢请求在 CPU 配额的快速间隙中被误判为恢复，已在 v2 修复；MongoDB v1 临时内存数据盘写满导致 WiredTiger 退出，该格 API/审计失败，排除性能与正确性结论，最终夹具改用 4GiB 普通临时磁盘，数据库 CPU/内存上限保持原值。更早调参的错误容器资源采样不用于 CPU 或 RSS 结论。

最终报告分别保留源文件/二进制身份、启动参数、原始采样、负载账本、审计和 SHA256。临时资源清理情况完成后记录。

## 如何使用这些结果

Weir 将协议、连接维护、请求合并、结果拆分与调度的工作承担在自身进程中。数据库仍执行索引查找、写入、持久化和复制，不能将这些成本移走。因此，数据库资源固定时可以获得收益，但系统总 CPU 可能增加，数据库内存也未必下降。

`max_read_size: 16KiB` 只适合已知小文档的数据集。不同文档大小、键分布、读写比例和延迟目标应分别调参；这里的批大小、收集窗口与并发上限是有实测依据的配置档案，并非所有业务的通用默认值。
