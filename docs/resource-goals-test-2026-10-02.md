# Weir 数据库减载、连接集中与背压验证（2026-10-02）

**数据库减载与连接集中已得到实证；背压能主动收缩并恢复，但恢复仍有波动，极低ES配额仍有超时和UNKNOWN。** 本轮重构、调参后的48格新性能对照均无API失败/UNKNOWN/OOM，共1388304笔APPLIED写入通过内容审计。最终生产构建为 **v3**，源码和二进制身份见 [build manifest](measurements/2026-10-02/build-manifest-v3.json)。旧生产基线为 `614eb443e298ffc531507a32743b15f5a4baea00`；v1/v2 的调参过程及失败记录独立保存，最终吞吐表均使用 v3 的新配对实验。

## 改动和参数

- MongoDB 同一物理批内只做一次 namespace 资格检查，再执行读写；单个 `_id` 使用等值查询，多个使用 `$in`。没有跨批保留 collection 状态或权限。
- 普通 Record Read 新增 `local.max_read_size`（1KiB–2MiB，默认2MiB），使已知小文档能够使用较小的结果预算、合并更多请求。超限读返回 `RESOURCE_EXHAUSTED`；写入、Scan、Native、Lua 保持现有文档边界。
- `local.batch_collect` 可选0–10ms，默认1ms。选择更长收集窗口来降低数据库每个请求的固定成本，同时明确报告延迟代价。
- ES JSON 校验和 bulk 回复处理减少重复解码与分配，保持 UTF-8、转义、重复键、深度和节点数检查；差分 fuzz 的215113个样本没有发现语义差异。
- 调度允许独立且工作内存预算足够的请求越过暂时不能执行的请求，保持会话与键的顺序约束。
- 成功但持续变慢的批次也能触发背压。最多64个延迟 profile，按目标、读写类型、批大小和平均输入大小分类；4个健康样本预热。一个至多1秒的证据段中，至少3个饱和慢完成、跨度至少100ms、超过基线2倍+2ms，且占该类健康批完成至少10%，才降低窗口或延长共享恢复 hold。取消不参与学习。显式拥塞立即减半；成功慢响应逐步减窗，窗口最低1，恢复不超过配置上限。

v3 修复了实测中的恢复问题：v2 在健康 ES 有 CPU 余量时仍会因零星 GC/CFS 尾部持续续 hold、锁住窗口1；v3 只在确认压力后续期。这里10%是同一 profile 的批完成/Scan页比例，证据段会重置，不能解释为全部记录的精确滑动窗口。

所有执行仍在一个 Weir 进程中，Lua 在主进程内运行。

## 性能测试方法

约1KiB文档、1000个预置读键，90%读/10%写和纯写两种负载，800/3200次每秒。每数据库24个新格：每种负载、到达率与路径各3次重复，交替路径顺序；预热10秒、测量20秒。直连与Weir使用同一负载生成器，64业务并发、有界队列256、排队过期100ms、从计划到达起算1秒deadline、不自动重试。

MongoDB 8.0.32 在隔离EKS Pod内运行，数据盘为4Gi普通临时磁盘；ES 8.19.22 在临时Docker夹具中运行。两个数据库的环境不同，不用于比较数据库间绝对性能。CPU是权威数据库/Weir进程的CPU秒差除以时间，单位核；RSS是测量期最大采样值，对3轮取中位数。内核100Hz ticks/4096字节页和实际cgroup配额均保存。连续数据库的RSS包含累积缓存。

成功、发送前client drop、API失败、UNKNOWN分开统计。每轮审计所有APPLIED写入的实际完整BSON/JSON内容；没有把UNKNOWN或未发送的写入计为成功。

本轮连接矩阵使用1/16个真实业务进程、相同总200/s、4000次只读请求。只读观察器交叉检查数据库进程的socket inode与TCP表，不为观察建立数据库连接。

16进程的实测连接 **32→5，减少84.4%**，四格无drop/API失败/admission拒绝/OOM。包含Mongo驱动监控连接，不能拿理论满池80当成实测32。此独立夹具为DB0.5CPU、Weir2CPU、pool4/sessions32/batch16/3ms/read16KiB；使用v2构建，v3仅修改延迟控制器、相关测试，后端连接实现完全相同。这个低速同步读场景平均批约1.04，**DB CPU没有下降**，不能把连接集中与CPU减载混为同一效果。停止Weir后数据库连接回到原始0基线，owner acquired/released守恒。

ES的独立较早生产版本矩阵在200/s全部成功时，16进程直连实际连接中位数16（范围16–32），经单Weir为4；800/s的双Weir全成功时为8，对照直连64。较早单Weir800/s仍有sessions拒绝，不能将该较低连接数当成v3满吞吐证明。HTTP也使用TCP池，所以ES同样能够集中连接。

完整版本、16个进程身份、raw socket样本、CPU/RSS和停止后的连接回收见 [连接报告](measurements/2026-10-02/connection-goals/connection-findings.md) 与 [哈希清单](measurements/2026-10-02/connection-goals/sha256.json)。连接上限预算与HPA示例见 [scaling](../deploy/kubernetes/scaling.md)。本轮没有实际触发MongoDB最大连接数耗尽，也没有部署HPA。

## 背压、降配和恢复

这组独立参数为32业务并发/会话、pool4/batch8/collect3ms/read16KiB、客户端队列32。持续同一数据库进程，运行中改变实际CPU配额；保留PID/start ticks、container ID、配额生效时间、窗口、恢复hold、latency/backend事件、API账本和审计。跨配额边界的十秒窗口也保留，但不与完整单阶段窗口混用。

MongoDB固定2500/s，实际CPU配额0.5→0.05→0.5，持续同PID/restart0/OOM0，普通磁盘4Gi。两轮均4→1并在低额保持；恢复期均出现1→2→3，再次收缩。

## 边界、验证与清理

- 这轮证实了选定负载下的数据库CPU节省与连接集中；总CPU一般增加，数据库RSS没有体现稳定的节省。批量不能移走索引维护、持久化或数据页缓存的固有成本。
- 更多Weir资源能够承接额外计算。本轮用2CPU充分测试，HPA示例另外保留；横向扩容仍要预算所有实例的数据库连接与并发，长连接客户端需要分流，CPU HPA也不自动解决sessions满的问题。
- 配置预算不能按约1KiB测试的低RSS直接收窄。未知大小的数据保留默认2MiB读上限；收集窗口以延迟要求和CPU收益选择。
- 改动是实现与参数的组合收益，并非单项优化的独立因果估计；[v2中间报告](resource-goals-v2-intermediate-2026-10-02.md)保留原生产对照与独立收集窗口调参，不与v3新对照混合。
- v1内存数据盘写满导致WiredTiger退出、错误容器/ES launcher PID采样、旧版CFS快慢交替、v2尾延迟锁hold和小队列drop都已保留。错误采样不用于进程CPU/RSS结论，失败格不计为成功。

v3 全量 `go test ./...`、相关包race、`go vet ./...`、integration helper测试、配置/HPA检查、`git diff --check`均通过。测量工具Python完整122个测试通过（正常4个显式skip，优化模式31个skip）；与测量相关的连接6个、最新ES权威PID/负载14个测试均无skip通过。integration helper测试不替代这里的真实数据库实验。详细验证与日志见 [validation](measurements/2026-10-02/validation.json)。

MongoDB两个v3夹具的owned namespace均独立确认NotFound，精确port-forward停止，原始归档与审计已保存。ES最终夹具owned containers/networks均为空、inventory精确恢复、errors=[]；较早pilot的Docker默认bridge ID漂移单独保留，不冒充所有历史轮次均精确恢复。各目录保存清理凭证。最终复核252个Go源码/模块文件仍与构建manifest一致，实测二进制始终为同一个v3构建。
