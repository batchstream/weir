# 有限资源下直连与 Weir 的 MongoDB / Elasticsearch 实测

测试日期：2026-10-01 至 2026-10-02（北京时间）。生产 Weir 源码为 `614eb443e298ffc531507a32743b15f5a4baea00`，本次只补充测试工具和测量报告，没有修改生产调度逻辑。

两种数据库分别在同一实例上比较直连与 Weir。数据库限制为 **0.25 核 CPU、1,536 MiB 内存**，Weir 为 **0.5 核、768 MiB**；另对 Elasticsearch 增加 Weir 1 核的复测。每个条件交替顺序 AB、BA、AB，三次测量，每次预热 10 秒、正式测量 20 秒。

在 3,200 次/秒的压力下，MongoDB 混合读写通过 Weir 的吞吐变化为 -41.9%，纯写为 +63.7%。Elasticsearch 的 0.5 核 Weir 在混合读写 / 纯写中分别变化 -23.8% / -8.6%。数据库 CPU 的降低不能单独视为节省资源，必须同时计算 Weir 自身 CPU 和未完成的负载。

Elasticsearch 给 Weir 1 核后，纯写吞吐中位数提高 8.7%，数据库 CPU 变化 -36.9%，但 Weir 自身使用约 0.57 核。混合读写在三对测试中没有一致收益。1 核组与 0.5 核组各有自己的直连基线，不能把不同组直接拼成 CPU 配额变化的因果结论。

## 测量方法与边界

- Elasticsearch 8.19.22，镜像 ID `sha256:a1cc67962f24c058c854acc6aab0d0adaefefc945c0bfaaebb52aba6129de160`。JVM 堆 512 MiB，一个写线程，队列 200，一个主分片，无副本。字段不索引，按 ID 实时读取，写入不等待 refresh，translog durability=request，数据目录为独占 1 GiB tmpfs。
- MongoDB 8.0.32，镜像固定为 `mongo@sha256:4968f22d0c6c10ef29952f3e807f62872ba22b3312f25803564fbfc08255efc2`。单主节点 replica set，WiredTiger 缓存 256 MiB，oplog 固定为 64 MiB，majority 写确认，保留默认 journal 配置，数据目录为独占 1 GiB 内存 emptyDir。主节点与客户端、Weir 在同一 Pod，通过 localhost 通信；EKS 节点上还运行其他工作负载，本文不把该节点视为独占硬件。
- 本地 Docker 的 Linux 内核为 7.0.12，MongoDB 拒绝在该内核启动；[MongoDB 官方发布说明](https://www.mongodb.com/docs/manual/release-notes/8.0/)列出 6.19–7.0.13 的不兼容范围。因此没有绕过启动检查，改用已有 EKS 上独占的临时 namespace；节点内核及镜像实际身份保存在原始 provenance 中。
- 负载为确定性的 1 KiB 文档；混合负载读取 1,000 个预建键，并使用 Put 写入唯一新键。MongoDB 两条路径使用相同的 BSON 和 replacement-upsert 语义：直连也调用客户端 bulkWrite（每次一条），Weir 可聚合多条。MongoDB 的 [majority 及 journaling 语义](https://www.mongodb.com/docs/manual/reference/write-concern/)使用默认配置。
- Weir 使用当前 `routeclient.Record` API：每条操作创建一个有限 Route 会话，四条复用 gRPC 连接，最多八个并行客户端 worker / Route 会话；这不是长期复用 Route 的流式吞吐测试。后端并发上限四，最大批次 16。Weir 是一个进程，没有 Lua 子进程。
- 768 MiB 是本次 Weir 配置的内存预算和容器限制，不等于实际 RSS。八个 Route 会话具有显式预算；不能只根据约几十 MiB 的 RSS 将容器限制降至 256 MiB 并期望相同会话容量。
- 固定开环到达率为 800 和 3,200 次/秒；客户端两核、2,048 MiB，队列上限 256，到达过期 100 ms，单请求截止时间从计划到达算起为一秒，无业务重试。先通过纯 pacing 验证：无丢弃，唤醒 p99 不超过 5 ms。低负载组用来观察开销，压力组用来观察吞吐、丢弃和资源上限。
- 各试验重新创建任务独占的集合 / 索引及读取样本；各负载先分别通过直连与真实生产 Weir 路径训练 20 秒。ES 初始化 / 训练时数据库为一核，正式测量为 0.25 核；MongoDB 始终为 0.25 核。ES 每次启动新的 Weir 进程；MongoDB 为同一个 Weir 进程连续测试，RSS 可反映此前试验的 Go 堆保留。MongoDB 直连试验中 Weir 保持空闲，后台拓扑监控可能产生少量数据库负载。
- 数据库 CPU 使用 `/proc` 进程 CPU ticks 的差值，RSS 使用 `/proc` 页数。ES 的 Weir CPU / RSS 使用自身进程指标；MongoDB 的 Weir 使用 `/proc`。容器另采集 `cpu.stat`、`memory.current`、`memory.events`。进程 CPU 包含服务实际诊断开销，不包含外部采样 shell；容器 CPU 包含采样 shell。MongoDB 及 Weir 在各自容器内每秒采样，按负载开始的时间戳选取正式20秒窗口；原始时间戳和实际覆盖长度均保留，CPU 是采样平均值。
- ES 诊断及 Docker采样约一秒一次；MongoDB 使用额外的 Go 采样进程在容器内每秒记录 `/proc` 和 cgroup，每次正式测量至少十五点且首尾覆盖至少十五秒。数据库与 Weir 的进程 CPU / RSS 不包含该采样进程，容器资源包含其开销。MongoDB 整组试验在 Pod 内连续执行，控制连接只查询整体进度并取回文件；控制命令重试不重复启动已锁定的试验任务，数据库操作不重试。结果通过压缩归档传输及 SHA-256 校验，避免截断 stdout 被当成完整证据。

这些是短时、内存存储、按 ID 的读写测试，不能代表持久磁盘 I/O、完整业务索引、全文搜索、多副本网络、长期内存泄漏或生产最大容量。出现客户端丢弃的档位也不能称为无损可持续容量。吞吐按测量到达队列的成功数量除以20秒计算；请求可在原始一秒截止时间内排空，原始记录保留排空时间及含排空的保守吞吐。

## 正确性与清理

共 60 次正式试验、2,688,000 次计划测量操作，成功 2,188,657 次，客户端丢弃 499,343 次，测量 API 失败 0 次，UNKNOWN 0 次。写后审计覆盖包括预热在内的所有计划写入；APPLIED 为 1,780,696 条，实际查到 1,780,696 条，原始审计逐条校验内容。采样记录的 OOM kill 为 0；远程采样异常 0 条，保存在证据中。

正式组清理回执均通过：ES 独占容器、网络和二进制镜像已移除，Docker inventory 恢复；MongoDB 临时 namespace 已删除并确认不存在。测试准备失败的试验未计入结果，其清理回执另存。另一个未显式限定 oplog 的先行组自动创建了 990 MiB oplog，在纯写压力阶段写满 1 GiB 内存数据目录，日志明确记录 `No space left on device` 和 WiredTiger panic；该组未用于本文性能统计，其原始日志与资源记录保存在 `storage-limit-probe/`。正式 MongoDB 组显式配置 64 MiB oplog，以控制任务运行过程中累积的复制历史。

测试工具通过 `go test ./...`、`go test -race ./internal/testutil/testcapacity`、`go test -tags integration ./internal/testutil/testcapacity`、`go vet -tags integration ./internal/testutil/testcapacity` 以及 Python 的10项编排测试（普通与 `-O` 模式）。默认 Go 测试没有连接这两个临时数据库；上述现场负载试验是实际数据库验证。
